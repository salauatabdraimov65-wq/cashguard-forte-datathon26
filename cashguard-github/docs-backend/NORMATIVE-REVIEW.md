# Нормативная проверка перед сдачей

Проверено **18.10.2026, Asia/Almaty**. Применён `ecc:research-ops`: лёгкая повторная проверка первичных источников, с разделением текста нормы, аналитического вывода и непроверенной применимости. ECC не предоставляет юридического эксперта; это исследование публичных источников, не юридическое заключение.

## Результат

Официальный Adilet открыл все четыре публичных акта в отдельной скрытой вкладке браузера. Подготовлен [каталог кандидатов](../../../contracts/legal-catalog.json): пять проверенных по тексту пунктов №231 с условиями и исключениями. **Он не связывает типы ML с нормами автоматически.** Приватные видео, кадры, описания эпизодов, XLSX и predictions исследователь не открывал. Из локального списка использованы только четыре публичных URL и номера пунктов.

`text_checked=true` означает прочтение **выбранного** текста, а не экспертизу всего акта. Во всех записях `edition_chain_checked=false` и `dataset_applicability_checked=false`. Подтверждение текста не является подтверждением нарушения на видео. Ни одной связи со статусом «подтверждено» этим исследованием не создано.

## Правила использования при интеграции

1. Сохранять оригинальный вывод ML отдельно от нормативной справки. Каталог не меняет внешний verdict и не превращает технический сбой в `no_violation`.
2. Не связывать правило с классом по ключевым словам. Для связи требуются согласованные наблюдения, контекст операции, проверка исключений и локальная проверка человеком. До этого показывать «применимость не подтверждена».
3. При недостатке контекста формулировать наблюдение и вопрос для проверки, а не уверенное юридическое обвинение. Название акта и пункт можно показывать как **кандидат основания**, явно отличая его от установленного нарушения.
4. Не выводить «телефон/вода/одна персона/открытая дверь = нарушение». По проверенным источникам общий запрет пить воду не установлен. Отсутствие видимого документа не доказывает отсутствия учёта, идентификации или документов в системе.
5. Номера пунктов из предоставленного списка без надёжной связи «акт—пункт» не считаются подтверждёнными соответствиями. Остальные перечисленные номера не исследованы полностью и не разрешены для автоматического подтверждения.
6. Для сдачи нужен локальный реестр **фактически поддерживаемых** типов ML → наблюдаемые условия → применимый кандидат/отсутствующее основание → проверка человеком. Этот исследователь не использует приватные сведения для его заполнения.

## Проверка и ограничения

- Четыре официальных URL доступны в обычном JS-браузере. `web.open` вернул JS-заглушку для первых трёх и недоступность четвёртого; это ограничение извлечения, а не доказательство отсутствия акта. Вкладка создана исследователем и закрыта после проверки.
- Информация и история №231 теперь прочитаны: прежний технический блок фазы2 частично снят. Полные отдельные акты поправок, официальные даты публикации каждой поправки и все переходные положения не проверялись; `edition_chain_checked=false` сохранён намеренно.
- Проверены выборочные положения и метаданные, не все пункты четырёх актов. Публичный JSON содержит только нормы, аналитические условия и статусы; кадров, описаний эпизодов, секретов и готовых юридических выводов в нём нет.
- Правовой специалист банка и ML-команда должны подтвердить предметную применимость. До этого нельзя утверждать, что требование кейса о корректном нормативном обосновании всех типов уже выполнено.

Следующий шаг: передать пять кандидатов ML-инженеру и участнику, отвечающему за нормы; локально проверить наблюдаемые предпосылки каждого реально выдаваемого типа. Неподтверждённые связи оставить явными, не заполнять догадками.
